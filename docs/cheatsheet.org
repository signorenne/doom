=F12= or =SPC h /= opens this sheet next to your buffer, at the section for
the mode you are in; =C-u F12= jumps to a heading instead, =C-u C-u F12=
searches the text. Inside the sheet: =TAB= unfold, =s= search the headings,
=S= the text (words in any order, matches as you type), =gr= rebuild the
generated tables, =q= close.

* How to read this sheet
Every section is folded. Open the one you need, read the small table, close
it again. The two reference sections at the end are generated from the
running config, so they are always true; everything above them is written by
hand and explains the parts that keys alone do not.

Three menus cover most of what this config adds. Each one shows the current
state in its header.

| Menu      | What it drives                   |
|-----------+----------------------------------|
| ~SPC k SPC~ | build, run and debug the project |
| ~SPC n SPC~ | notes, tasks and the agenda      |
| ~SPC l SPC~ | AI agents                        |
| ~SPC s SPC~ | searching and replacing          |

=SPC= is the leader, =SPC m= the localleader for the current mode, and
=SPC m SPC= a menu of what the mode can do: dired, ibuffer, info, bookmarks,
re-builder, the agenda; =C-o= in calc and isearch, which have no evil state.

On the dashboard he talks to himself: the greeting, a word of his own
or a hint from this sheet, a new one every twenty-five seconds or so.

~SPC h j~ summons the butler: he comes with a hint for the mode you are
in, taken from this sheet, and his menu opens. ~q~ closes the menu and he
stays; ~SPC h j~ again brings the menu back; ~x~ in it, or ~SPC h J~, and
he goes. The menu moves him: the corners on ~7 9 1 3~, the middle on ~5~,
below the cursor on ~0~, a step with the arrow keys; or drag him with the
mouse. He is found where he was left, next session as well. ~a~ in his
menu asks him a question in your words, "change the date of a commit":
he answers from this sheet and the READMEs with the key, the section it
is under in the corner of the bubble; when the words leave it open he
says the best answer and offers the rest in a numbered menu, ~1~ to ~5~,
to choose between, ~c~ there asking Claude instead; and he puts it to
Claude, through gptel or, with no API key set up, through the Claude
Code command line, when the words do not settle it or when asked with
~C-u~; ~A~
asks Claude outright, for a hard question or one the sheet cannot
answer at all, since Claude keeps to the docs only where the question
is about this configuration; and ~r~
puts the last question to Claude when what he said was not what you
meant; ~o~ opens the docs at the line. He says twelve lines at the most,
and ~R~ reads the whole of a long answer in a buffer, ~c~ copies it.

Getting out is one rule everywhere: =q= closes a menu or a read-only buffer,
=ESC= closes a popup or cancels a prompt, and =C-`= brings the last popup
back. The window a program left behind takes either, =q= or =ESC=. In a menu
that used =q= for a command of its own, that command is on =Q=: quit dired,
quit calc, bury magit.

* Doom
** Config files
| File                                 | What lives there       |
|--------------------------------------+------------------------|
| =init.el=                              | the module list        |
| =config.el=                            | identity, fonts, theme |
| =packages.el=                          | cross-cutting packages |
| =modules/private/<name>/config.el=     | a module's settings    |
| =modules/private/<name>/packages.el=   | its packages           |
| =modules/private/<name>/autoload/*.el= | its commands           |
| =docs/cheatsheet.org=                  | this sheet             |

To add a package, put =(package! name)= in a module's =packages.el=, then
=SPC h r s=. A package that is not on MELPA needs a recipe:
=(package! name :recipe (:host github :repo "owner/name"))=.

Every declaration carries a =:pin=, the commit installed here, so =doom
sync= on another machine installs the same versions. =M-x
doom/bump-package-at-point= on the line moves the pin to the newest
commit (=doom/bump-packages-in-buffer= for the whole file), then =SPC h r
s= installs it. =doom upgrade= leaves pinned packages where they are.

To add a module, create =modules/private/<name>/= and add its name to the
=:private= block in =init.el=.

** Undo, registers, macros
| Key       | What it does                                 |
|-----------+----------------------------------------------|
| ~u C-r~     | undo, redo                                   |
| ~U~         | every state the file has been in, as a graph |
| ~"ay "ap~   | yank to, paste from a register               |
| ~q a ... q~ | record a macro into ~a~                        |
| ~@a~        | play it back                                 |
| ~SPC i y~   | the kill ring                                |

~u~ undoes one edit, and typing a word at a time, not all that was typed
in one go in insert state. Emacs keeps every state a file has been in,
the ones undone too, and ~u~ and ~C-r~ walk one path through them: an
edit after an undo puts the rest out of their reach. ~U~ draws all of
them as a graph along the bottom, the newest on the right, and the file
follows you through it; ~RET~ keeps where you are, ~q~ puts it back. The
lines an undo or a step changes light up for a moment. ~SPC t u~ shows
the graph for a moment at each ~u~ and ~C-r~ as well, and ~SPC s u~ is
Doom's key for ~U~. If a step cannot be made, the graph says so and is
drawn again from the text as it is; ~RET~ always leaves it, keeping what
is on screen.

|-------+-------------------------------------------------------------------|
| ~h l~   | an older state, a newer one; at a fork ~l~ goes back the way ~h~ came |
| ~j k~   | the branch drawn below, above, from any state on this one         |
| ~H L~   | the start and the end of this branch                              |
| ~s S~   | the state last saved, the next saved one                          |

*** The menu
~SPC s SPC~ holds the same searches with the options in front of you, and
the replaces with them. Press the letters for what you want, then the
letter for where to look:

| Set | What it means                              |
|-----+--------------------------------------------|
| ~F~   | a literal string, not a regular expression |
| ~w~   | whole words only                           |
| ~i~   | either case                                |
| ~v~   | the lines that do not match                |
| ~m~   | a match may cross line ends                |
| ~g~ ~G~ | only the names matching, every name but    |
| ~t~ ~T~ | only one kind of file, every kind but      |
| ~u~   | the ignored and hidden files too           |
| ~c~   | lines of context round each match          |

| Then    | Where it looks                                  |
|---------+-------------------------------------------------|
| ~p d D P~ | the project, here, a directory, another project |
| ~*~       | the word under the cursor                       |
| ~b l~     | every open buffer, this buffer                  |
| ~r~       | replace: the same places, in its own menu       |
| ~R~       | replace in the project, without asking where    |

~r~ opens the replace menu, which asks where with the same letters the
search column uses: ~l~ this buffer, ~p~ the project, ~d~ this directory, ~D~
one it asks for, ~P~ another project, ~f~ the files marked in dired. What
you set above is carried into it and written at its top, so a replace
is never wider than the search you were about to run.

In the results of any of these: ~C-j C-k~ move, ~RET~ goes there, ~C-c C-e~
turns them into a buffer you can edit and ~C-c C-c~ writes it back, and
a second ~#~ filters them without asking ripgrep again.

A replace never opens a file that does not hold the text: ripgrep is
asked first, with those same options, and only what it names is
visited. It asks at every match, ~y~ and ~n~ as always, ~!~ for the rest of
a file, ~q~ to stop. The word under the cursor is offered as the thing
to replace. ~f~, the files marked in dired, is the exception: that one is
Emacs's own command, which asks for its own regexp and visits every
file marked, flags or no flags.

*** Narrowing it by hand
What the menu sets can be typed instead, which is worth knowing when
the search is already open.

What you type after the ~#~ is a regular expression, given to ripgrep as
it stands: =popup.*[Bb]ridge= is a search, and a literal =(= or =*= has to
be escaped or searched for with =-F= below. A second ~#~ filters the
results again inside Emacs, without asking ripgrep anything: =#bridge#.h=
keeps the lines whose path or text holds =.h=.

Anything after a lone =--= goes to ripgrep itself, which is how a search
is narrowed to certain files:

| After =--=       | What it does                                   |
|----------------+------------------------------------------------|
| =-g '*.h'=       | only files whose name matches                  |
| =-g '!*.pc.cpp'= | every file but those                           |
| =-tcpp=          | a language ripgrep knows, =--type-list= has them |
| =-F=             | literal: no regexp, for =foo(= and =a*b=           |
| =-w=             | whole words only                               |
| =-i= =-s=          | ignore case, respect it                        |
| =-A2 -B2=        | lines of context after, before                 |

So =#PopupAudioBridge -- -g '*.h'= searches the headers alone. The same
works for ~SPC s d~ and ~SPC s D~, which are the same search in a directory.

** Replacing
Five ways, by how far the change reaches and how much you want to see
of it first.

| Key         | What it changes                                                                    |
|-------------+------------------------------------------------------------------------------------|
| ~SPC c r~     | one symbol, everywhere: the language server renames                                |
| ~:%s/a/b/g~   | this file, evil's own; ~:%s/a/b/gc~ asks at each match                               |
| ~SPC s SPC r~ | the menu: this buffer, the project, a directory, another project, the marked files |
| ~SPC s R~     | the project at once, the files that hold it                                        |

~SPC c r~ is the one to reach for on a C++ name: the server knows which
words are that symbol and which only look like it, and it follows the
name into the header. Everything below it is text, and text does not
know a comment from a declaration.

~SPC s R~ asks ripgrep which files hold the text before it starts, so it
opens those and no others; the options set in ~SPC s SPC~ narrow that
list, and ~F~ there makes the text literal. It asks at every match: ~y~ and
~n~ as always, ~!~ for the rest of a file, ~q~ to stop.

When you want to see every change before any of it happens, go the long
way: search with ~SPC /~, ~C-c C-e~ turns the results into an ordinary
buffer, edit that buffer as text, and ~C-c C-c~ writes every file back.

a buffer. ~C-o~ takes you back to where you started.

the compilation database. ~SPC k I~ tells you, ~SPC k m z~ fixes it.

** Recipes
- *Where is this used?* cursor on it, ~gD~. Or ~SPC *~ for the plain
  text, which also finds comments and strings.

** Images
A raster image, PNG, JPEG, GIF, WebP, BMP or an icon, opens the way an
SVG does: what is inside it on the left, the picture on the right.

- *The picture*: format, size, shape and megapixels, pixel type, bits a
  pixel and how far the file compresses the raw pixels, density, frames
  and duration when it is animated, and whether it carries a colour
  profile. A file named =.png= that is really a JPEG says so.
- *Colours*: how many distinct colours, how much is transparent or partly
  so, or that an alpha channel carries nothing, the mean colour, the
  dominant ones, and each channel's range, mean and histogram.
- *Structure*: the format's own parts, each with its offset and length.
  A PNG's chunks, =IHDR= with the size and bit depth, =pHYs=, =iCCP=, the
  =IDAT= pixels, =IEND=; a JPEG's markers, =APP1= with its EXIF, =SOF= with
  its dimensions and whether it is progressive, each scan; a GIF's
  frames; a WebP's RIFF chunks.
- *Metadata*: what exiftool reads, camera, date, software, GPS, grouped.
- *Bytes*: all of a small file in hex, the first kilobyte of a large one,
  where the chunk names above can be seen at the offsets they give.

A file that is cut off or damaged is described as far as it goes, and
the place it stops is said. The report is =bin/inspect-image=, which runs
in the background, so a large file never holds up the editor; it was run
over every image on this machine, 9 700 of them, without a failure.

An SVG opens as its XML, with the drawing on the right, drawn again
after each pause in the typing. It is drawn over a checkerboard, the
way every image editor shows transparency: an icon drawn for a light
interface is dark strokes on nothing, and would vanish on a dark theme.
The squares are mid-grey rather than white, so a white icon shows too.
Halfway through a tag the XML does not parse, so the drawing stays as it
was and its header says which line is broken. One exported as a single
long line is taken over by ~so-long-mode~ and keeps its drawing.

** How to, step by step
- Look at a file without opening it: put the cursor on it. The pane on
  the right shows it. ~F~ if the pane is in the way, ~F~ again for it back.
- Find a file whose name you half remember, anywhere below here:
  ~SPC m f~, type a word or two of it, ~RET~. Every file below with those
  words in its path is listed; ~M-n~ narrows that further, ~RET~ opens
  one, ~q~ leaves. Or ~SPC f F~, type, ~RET~, when you only want to open it.
- Search the whole tree as you type: ~SPC m f RET~ lists everything
  below, then ~M-n~ and type.
- Find it in this directory only: ~M-n~, type, watch the list shrink.
- Copy a file into another directory: ~m~ on it (or nothing, for the one
  under the cursor), go to the directory with ~h l~, ~b~ or ~z~, ~p~.
- Move it instead: the same, ~SPC m m~ at the end.
- Move files between two places you keep going back to: ~SPC m 2~, the
  other pane; ~b~ or ~h l~ in it to where they go; ~C-w h~ back, ~m~ the
  files, ~R~: the other pane is the offered destination, ~RET~.
- Hand a file to another program: drag it out of the listing with the
  mouse and drop it in the window, or ~yc~ and paste there.
- Copy or move to a directory you would rather type: ~C~ or ~R~, then
  the path, with completion.
- Rename one file: ~R~, type the new name. Rename many: ~i~, edit the
  names as text (=:%s/old/new/= works), ~ZZ~; ~ZQ~ if it went wrong.
- Make a file here: ~a~, its name. A directory: ~a~, its name ending
  in =/=.
- Delete: ~d~ on each, then ~x~; or ~D~ for the marked ones at once.
  Both ask first, and the files go to the trash, the same one Finder
  or Dolphin shows. Deleted the wrong thing: ~SPC f t~ opens the trash,
  newest first, ~m~ on it, ~SPC m t~ puts it back where it was.
- A copy beside the original, to try something on: ~yd~.
- Send a file to another app: ~yc~, then paste there. Bring one in: copy
  it in Finder or Dolphin, ~yv~ here.
- Copy the path for a terminal or a chat: ~SPC f k~, pick the form.
- See how big a directory is: cursor on it, ~f s~.
- Open it in the desktop app, or the directory in Finder or Dolphin: ~E~.
- Open a terminal here: ~SPC o T~.
- Two directories side by side: ~SPC w v~, ~SPC f d~ in the new window,
  navigate; ~C~ and ~R~ now offer the other side as the destination.

* Git
~SPC g g~ is the status buffer, and everything starts there: a key is a
menu of what you can do with the thing under the cursor, ~?~ shows them
all. The keys below are the ones evil leaves you, which differ from
magit's manual in a few places: ~x~ discards, ~o O~ reset, ~p~ pushes,
~Z~ is the stash menu and ~%~ the worktrees, ~z~ folds. ~SPC g SPC~ is a
hub of the everyday commands in plain words, ~SPC g h~ everything that
rewrites history, ~SPC g n~ everything about branches. Every magit
buffer opens this chapter with ~F12~.

The log prints a commit's refs after its summary, so every summary starts at
the same column and the eye runs down them; the graph's lines carry the
theme's colours, one per branch, which takes both =log.graphColors= in
=~/.gitconfig= and =--color= among the log's arguments: magit leaves that
switch off, so the config turns it on. ~l~ then ~-c~ toggles it for one log.
A diff takes its tab width from the file's own mode, flags a line indented
with the wrong character, hides the =^M= of a CRLF file, and runs the hunks
through =delta=, which colours the code inside them as the language it is
rather than all green or all red. delta must not be given =--line-numbers=
or =--hunk-header-style omit=: magit re-reads the diff it printed, and
either one makes it unreadable. The status buffer carries a TODOs section,
grouped by directory, from the same scan ~SPC p t~ uses.

A hunk too big to be one change: ~V~, ~j~ down to where the first change
ends, ~s~. What is staged is what the commit will hold, whatever the
buffer says; the status buffer saves the file buffers first.

** Committing
| Key | What it does                                                |
|-----+-------------------------------------------------------------|
| ~c c~ | commit what is staged                                       |
| ~c a~ | amend the last commit with what is staged, edit its message |

| ~c n~ | augment: squash into an older commit and edit its message   |
| ~c R~ | reword an older commit, folded in by the next ~r f~           |

then why. ~C-c C-t~ writes =type(scope): = with the
type asked and the scope read off the staged files. ~M-p M-n~ bring

commits, ~ZQ~ throws it away. =bin/check-commit-msg=, linked as the
commit-msg hook in the config repository, refuses a subject that is not
=type(scope): what=. The scope is not optional, the what is in the
imperative, and there is no length limit.

** Guides, step by step
Each starts in the status buffer, ~SPC g g~. "In the log" means ~l l~ there,
the cursor on a commit. Where a command needs a commit and the cursor is
not on one, it either lists the latest commits, hash, date and subject,
where typing a word of the message finds one and ~RET~ takes it, or opens
a log to choose from, where ~C-c C-c~ takes the commit under the cursor
and ~C-c C-k~ gives up. A message opens in its own buffer: write it, ~ZZ~
to go on, ~ZQ~ to give up.

Any commit changed after it was pushed has to be pushed with force, see
"Push after rewriting". A commit not pushed yet is yours to change freely.

*** Change the last commit's message
1. ~c w~: the message opens.
2. Edit it, ~ZZ~.

*** Change an older commit's message
1. In the log, cursor on the commit.
2. ~r w~, or ~w~ in ~SPC g h~: the message opens.
3. Edit it, ~ZZ~. The commits after it are replayed on top, by themselves.

*** Add forgotten changes to the last commit
1. Stage them: ~s~ on the files or hunks.
2. ~c e~ keeps the message; ~c a~ opens it to edit as well.

*** Add forgotten changes to an older commit
1. Stage them.
2. In the log, cursor on the commit that should have had them.
3. ~c F~: they are folded into it and the commits after it replayed.
   With ~c f~ instead, a fixup! commit is made now and ~r f~ folds it in
   later, with others.

*** Change the date of a commit
1. In the log, cursor on the commit; or from anywhere, and pick it.
2. ~SPC g h d~.
3. The date: =2026-09-01 14:30=, or =+2d 9:00=, =-1w=, or pick it in the
   calendar that opens. ~RET~.
Author and committer date both change. For an older commit the ones
after it are replayed: their author dates stay, their committer dates
become today, as any rebase does. ~c d~ changes the last commit's date
the same way, from magit. Several in a row: ~r t~, see "Squash, reorder
or drop several commits".

*** Change the author of a commit
1. In the log, cursor on the commit; or pick it.
2. ~SPC g h a~: =Name <email>=, filled in with the current one.
3. Edit it, ~RET~.

*** Take back the last commit
~SPC g h u~: the commit goes, its changes stay staged, ready to commit
again otherwise. To drop the changes too: in the log, cursor on the
commit before it, ~O h~. Either way the reflog, ~l r~, still has it.

*** Push after rewriting
A rewritten commit is a new commit: the remote still has the old one and
refuses a plain push.
1. ~p~, then ~-f~ (force with lease), then ~u~.
2. With lease, the push is refused if someone else pushed to the branch
   since you fetched, so nothing of theirs is lost. Then ~f u~ to fetch,
   ~r u~ to put your commits on theirs, and push again.
~-F~ is force without the check: it overwrites whatever is there. Never on
a branch others push to.

*** Cherry-pick a commit from another branch
1. ~l o~, the other branch, ~RET~: its log.
2. Cursor on the commit, ~A A~: a copy of it is committed on your branch.
3. Several: ~V~, ~j~ to select them, then ~A A~; they go in oldest first.
~-x~ in the menu before ~A~ notes in the message where it came from. ~A a~
applies the changes without committing, to adjust them first. ~A d~
donates the commit under the cursor to another branch: it leaves this one.

*** Merge a branch into this one
1. ~m~, then ~m~ again, and pick the branch.
2. It fast-forwards when it can. ~-n~ in the menu first makes a merge
   commit every time, which keeps the branch visible in the log.
~m p~ previews what the merge would bring, ~m s~ squashes it into staged
changes you commit as one commit, ~m e~ opens the merge message to edit.

*** When a merge, rebase or cherry-pick stops on a conflict
1. The files are under "Unmerged" in status; ~RET~ opens one.
2. ~]n~ to the next conflict, ~SPC g x~ for the menu: ~u~ keep upper, ~l~
   keep lower, ~a~ both, or edit by hand. Save.
3. In status, ~s~ on the file: it is resolved.
4. Go on: ~m m~ for a merge, ~r r~ for a rebase, ~A A~ for a
   cherry-pick. Or give up and put everything back: ~m a~, ~r a~, ~A a~.
In a merge upper is this branch, in a rebase upper is the branch you
rebase onto and lower your own commit.

*** Bring your branch up to date with main
1. ~f a~: fetch everything.
2. ~r e~, =origin/main=, ~RET~: your commits are replayed on top of it.
3. A conflict stops it: see above, then ~r r~.
4. It was pushed before: push after rewriting, ~p -f u~.
~SPC g n m~ starts a new branch from main, fetched first.

*** Squash, reorder or drop several commits
1. In the log, cursor on the oldest commit to touch.
2. ~r i~: a list of the commits, oldest at the top.
3. On each line: ~s~ squash into the one above (both messages kept), ~f~
   fixup (this message dropped), ~r~ reword, ~e~ stop to edit, ~d~ drop;
   ~M-k M-j~ move a line up, down.
4. ~ZZ~ runs it; ~ZQ~ leaves everything as it was.
5. Reordered commits keep their dates, now out of order. ~r t~, cursor on
   the first of them, ~C-c C-c~, a date, ~RET~: it gets that date and each
   one after it the next minute. The date offered ends the run at the
   present minute; ~M-p~ offers one right after the commit before.

*** Split a commit in two
1. In the log, cursor on it; ~SPC g h s~: its changes come back unstaged.
2. Stage the first piece (~s~, or ~V~ lines then ~s~), ~c c~, a message.
3. The same for the rest.
4. When it was not the last commit: ~r r~ replays the ones after it.

*** Undo a commit that was pushed
In the log, cursor on it, ~_ _~: a new commit that undoes it, message
ready, ~ZZ~. Push it normally; nothing is rewritten. ~_ v~ puts the undo
in the files only, to commit yourself.

*** Tag a commit, a branch or HEAD
~t~ opens the tag menu in any magit buffer, ~T~ in ~SPC g SPC~ from anywhere.
- A commit: ~t t~, the name, ~RET~. The list shows every branch's latest
  commits with the branches and tags already on them, the one under the
  cursor first. Type a word of the message, or a hash, even of a commit no
  branch holds any more; ~RET~.
- The head of a branch: ~t b~, the name, then the branch, listed with its
  last commit.
- Where you are: ~t h~ and the name.
~-a~ in the menu first makes an annotated tag, with a message. Tags stay
local until pushed: ~t P~ or ~p T~ one tag, ~p t~ every tag.

*** Delete or move a tag
- Delete: ~t x~ removes it here only, ~t X~ here and on the remote, after
  a yes. ~t p~ prunes instead: it first offers to delete here every tag
  the remote does not have, the ones not pushed yet among them; answer no
  to those.
- Move: ~t~, ~-f~, ~t~, the same name, the new commit. Then ~p~, ~-F~,
  ~T~ and the tag, since the remote has it on the old commit.

*** Put work aside for a moment
~Z z~ stashes everything with a message; the tree is clean. ~Z p~ on the
stash puts it back and drops it, ~Z a~ keeps it. ~-u~ in the menu takes
untracked files too.

*** Commits made on the wrong branch
~b s~ and a new branch name: they move to it, and the branch you were on
goes back to where it was before them.

*** Throw away every change not committed
In status, cursor on "Unstaged changes", ~x~; on "Staged changes" as
well. Saved files were kept in the WIP log, ~SPC g h L~.

*** Get back what a reset or a rebase took
1. ~l r~: every place HEAD has been, newest first.
2. ~RET~ shows one; cursor on the one before the mistake.
3. ~O h~: the branch is back there.

*** Who changed this line, and why
~SPC g B~, then ~RET~ on the line: the commit. ~SPC g L~ is the file's
history; ~l l~, ~-S~ and the text finds the commit that introduced it.

** When a merge or rebase conflicts
The file opens with the markers in it and smerge is already on, so the
conflicts are marked up rather than raw text.

| Key     | What it does                                   |
|---------+------------------------------------------------|
| ~]n [n~   | the next conflict, and the one before          |
| ~SPC g x~ | the menu: which side to keep, and what differs |
| ~u~       | in that menu, keep mine, the upper one         |
| ~l~       | keep theirs, the lower one                     |
| ~b~       | keep the base, as it was before either         |
| ~a~       | keep both, one after the other                 |
| ~c~       | keep the one the cursor is in                  |
| ~e~       | ediff this one, when the two are close         |
| ~R~       | refine: what differs inside the conflict       |
| ~r~       | resolve it, when it is obvious                 |

~]n~ goes on to the next file that conflicts once this one is clean, so a
whole rebase is walked with ~]n~ and one letter at each stop. When every
conflict in a file is settled, stage it the ordinary way, ~SPC g g~ then
~s~, and carry on: ~r r~ for a rebase, ~m m~ for a merge, ~A A~ for a
cherry-pick, or ~C~ in ~SPC g h~. ~SPC g r~ is not it: that reverts the
change under the cursor.

| ~SPC k I~ | the project status: what is set up and what is missing                       |
| ~SPC k w~ | write the whole setup to .dir-locals.el, every kit whole                     |
| ~SPC k G~ | generate the presets from it: cmake --preset does what Qt Creator does       |
| ~SPC k U~ | deploy to the device, then ~SPC k r~ runs there                                |

The kit is read from the project, never asked: the one chosen for this
project if you have chosen one, else Qt Creator's active configuration
when it has one, else the newest configured build directory, else a
preset, else =build=. A kit you pick by hand therefore wins over
everything the disk suggests, and keeps winning until you pick another.
A kit whose compiler lives in a distrobox runs every command there, with
the SDK environment sourced: build, run, gdb, clangd, clang-tidy. Its
=LD_LIBRARY_PATH= is left out: the PC target's kits point it at the
target's libraries, and the container's own programs, clangd first,
crash on them. Buffers are saved before every build, run and debug. Qt
Creator's run configuration gives the executable, its arguments and its
working directory.

~SPC k y~ is the Debug and Release switch: it goes to the kit of that
type in the current kit's family, the other Qt Creator configuration,
the other preset, the other directory. One that was never built is
configured first, from the current kit's own settings, compilers,
generator, toolchain, Qt; one that does not exist is made, =build/Release=
beside a plain =build=. Then ~SPC k b~ builds it and ~SPC k y~ Debug
brings you back. A preset project uses its presets: =release= with
RelWithDebInfo answers RelWithDebInfo, and a type no preset declares is
made beside them. A configuration Qt Creator planned but never built,
=horizon-sdk-RelWithDebInfo=, is a kit too, and configuring it takes the
arguments Qt Creator gave it, sysroot, toolchain file, host path; a
toolchain file among them is a whole tool set, so a fresh clone with
nothing built configures from Qt Creator's file alone, in the container
that has the SDK.

A family is a Qt Creator kit or the plain directory: fdc-mule has
=KIT - HORIZON ARM64=, =KIT - HORIZON PC=, =horizon-pc= and =local-pc=.
~SPC k Y~ moves between them keeping the type; a family with no built
kit and no Qt Creator kit of its own cannot lend a tool set, so build
one there once.

Qt Creator's settings are read whole, on the host or in the container
whose home holds them: the kit behind each configuration brings its
compilers, Qt, environment and device, so a configuration never built
configures the way Qt Creator would, and a kit defined in a container
runs there without a probe. ~SPC k w~ writes every kit down in
=.dir-locals.el= and ~SPC k G~ as presets, after which
=cmake --preset horizon-sdk-Release= in the container, or ~SPC k K~
here, does the same with no Qt Creator around. A Ninja Multi-Config
kit lists its configurations instead of types: ~SPC k y~ picks the one
every build passes as =--config=.

* Data files: JSON, YAML, TOML, XML, CSV
Validation is the point. JSON, YAML and TOML each have a language
server, so a file is checked while you write it: a bad comma is
underlined where it is, not reported when you try to use the file. Both
the JSON and the YAML server also check against SchemaStore, so a file
they recognise, =package.json=, =tsconfig.json=, a compose file, a GitHub
workflow, is held to its real schema: ="name": 123= in a package.json is
an error, and so is a misspelt =runs-on=.

The YAML server fetches SchemaStore's catalog itself. The JSON server
does not, so the catalog is fetched here, kept for a week in Doom's
cache, and handed to it when it starts; ~M-x +data/refresh-schemas~
fetches it now.

The same four keys work in every one of these formats.

| Key       | What it does                                     |
|-----------+--------------------------------------------------|
| ~SPC m v~   | say whether this file is valid, and take you to where it is not |
| ~SPC m =~   | prettify: laid out to be read, comments kept     |
| ~SPC m -~   | compact: as few lines as it will take, where nothing is lost |
| ~SPC m ?~   | what this file is taken for, and what is checking it |

** What SPC m v checks
=bin/check-data= reads each format with its own real parser, so the
verdict is the one the tools that consume the file would give. It was
run over every data file on this machine, 3 409 of them, and every file
it calls invalid really is.

| Format | Invalid when                                                      |
|--------+-------------------------------------------------------------------|
| JSON   | it does not parse; see below for comments                         |
| YAML   | it does not parse; a tag it does not know, =!Ref=, is still valid    |
| TOML   | it does not parse, as TOML 1.0                                    |
| XML    | it is not well formed; it is not checked against a schema         |
| CSV    | its quoting is broken, which swallows every row after it          |
| INI    | a key or a section is set twice, or a line is none of the three  |

JSON with comments and trailing commas is decided by name, the way VS
Code decides it: =tsconfig.json=, =devcontainer.json= and anything in
=.vscode/= may have them. Anywhere else they are an error, at the
column they are at, since npm, node and every strict reader refuse them.

A CSV whose rows are not all the same width is not invalid: many real
formats leave off an optional last column, ESP-IDF's partition tables
among them. It says so, as a count of rows of each width. A =.conf= file
is not checked at all: it is nginx or systemd or anything else, and
checking it as INI would be wrong. An empty JSON file is invalid, since
JSON needs one value, even ={}=.

** Reshaping a file
~SPC m =~ and ~SPC m -~ replace the buffer, and refuse to when the tool
cannot read the file, so a broken file is never made worse by
formatting it. They keep what the author wrote:

- JSON goes through =jq=, which lays out every value and keeps big numbers
  exactly; JSON with comments goes through prettier, which keeps them.
- YAML goes through prettier. Not through a YAML library's dump: a dump
  drops every comment, and a YAML 1.1 reader turns the key =on= into
  =true=, which is how a GitHub workflow would lose its trigger.
- TOML through taplo and XML through xmllint, both of which keep comments.
- In a CSV the same keys align and unalign the columns.

Compact refuses where it would lose something: YAML, whose compact form
cannot hold a comment, JSON with comments, and TOML.

** The preview
Opening a diagram opens its preview beside it; you do not ask for it.
The window appears at once saying it is drawing, and the diagram
replaces that when it arrives, because the first drawing of a session
has a JVM to start. Move to another diagram and the preview follows.

The redraw waits for a pause in the typing, so a burst of keys costs one
drawing rather than one per key. A diagram opened in the background, by
a search or an export, opens no window and starts no server. The
preview is a window you can move into, ~C-w l~, to zoom a large diagram
with =+= and =-= and pan it with =h j k l=; ~q~ there closes it until
~SPC m p~.

The drawing is coloured for your theme, not for paper: PlantUML puts its
background in a CSS style that Emacs's renderer ignores, so on a dark
theme an unadjusted diagram is dark text on a dark background.
~+uml-preview-theme~ is =auto= and passes =-darkmode= when the frame is
dark. What ~SPC m e~ writes out is unaffected.

** Why a server is running
PlantUML is a Java program: rendering by running it costs about a second
each time, far too slow to follow typing. It can serve its own picoweb
server instead, where the first drawing pays for the JVM and every one
after it costs about 30 milliseconds. Measured here: 1.7 s, then 0.03 s.

So the first preview starts =plantuml -picoweb= and it stays. It listens
on 8135, or the first free port above it, so two Emacs sessions do not
fight over one.

** Grammar, and reading a PDF
LanguageTool reads a buffer and says what is clumsy in it, not only
what is misspelt. The language is detected per buffer, so a note in
Italian is read as Italian and one in English as English, and Italian
is named as the mother tongue, which is how it catches the words that
look like the English ones and are not.

A PDF opens in ~pdf-view-mode~: ~j k~ scroll, ~n p~ turn the page, ~/~ searches
the text, ~o~ shows the outline, ~SPC m~ has the rest. Org can link into

minute. Put it in =~/.local/bin= and a =doom sync= cannot lose it again.

** Emacs and packages
| Symptom                         | What to try                              |
|---------------------------------+------------------------------------------|
| a command is missing in the GUI | =doom env=, then restart                   |
| odd errors after an upgrade     | ~SPC h r s~, then =doom doctor=              |
| a tree-sitter mode looks plain  | =M-x treesit-install-language-grammar=     |
| the native-comp warnings buffer | harmless, close it                       |
| vterm is missing                | =M-x vterm-module-compile=                 |

Grammars install themselves the first time you open such a file, so a plain
looking buffer usually means the install failed; the command above says why.

A pause that comes now and then, in one file and not another, is seldom
caught by trying again. ~SPC t W~ watches while you work and writes down
every key that took over 50 ms to answer, every timer that ran as long
and every garbage collection, each with the buffer and mode it happened
in; ~SPC h D~ shows the list, and the name on the slow line is the thing
to look at. It costs a little while it watches, so turn it off after.

The profiler names what is burning time; =C-c C-c= on a line opens it. The
usual suspects here are a repeating timer (every tick is a redisplay),
something on ~post-command-hook~, or a preview of a huge file. What is known
to be fast: a 47 MB log opens in 0.2 s, a 2 MB C header in 0.5 s, a C++
buffer of the fdc project comes back in 0.3 s with its server attached half
a second later, and a cursor move in dired costs 2 to 6 ms.

A file over a megabyte opens with the spell check, eldoc, smartparens,
the diagnostics, the line band and the diff gutter off and fewer colours,
and in the mode Emacs had before tree-sitter, cc-mode for C and C++:
typing in it stays under 10 ms. =M-x so-long-minor-mode= gives the rest
back.

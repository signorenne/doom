#+title:    :private notes
#+subtitle: documents, capture, agenda and roam

* Description
Everything written lives in one vault, ~+core-notes-dir~, =~/notes= on
this machine (set in =init.el=): org notes, PlantUML diagrams and
pictures. The vault is ~org-directory~ and ~org-roam-directory~ at once,
one Org-roam graph where Zettelkasten knowledge and PARA work meet, and
one git repository that commits itself. Books and papers are a library
apart, ~+notes-library-dir~, which only citar reads.

- the inbox =inbox.org= and one =projects/<slug>/index.org= per
  bounded outcome, with Dashboard, Goal, Completion criteria, Next
  actions, Decisions, Progress and Knowledge and sources,
- seven documents, each a node of the graph, created from =templates/org=:
  the inbox, the project index, someday, reading, snippets, habits and
  University. See ~+notes-documents~,
- courses, lectures, case studies, design documents and decisions, with
  live tables and boards in the notes, see [[*Work and study][Work and study]],
- captures that write into the inbox or the owning project, including the
  region as a code snippet and a bug report with a link back to the line,
- an [[https://github.com/alphapapa/org-super-agenda][org-super-agenda]] dashboard and a weekly review, plus [[https://github.com/alphapapa/org-ql][org-ql]] queries,
- org-roam for lasting notes, with dailies as the journal, [[https://github.com/jgru/consult-org-roam][consult-org-roam]]
  for search and backlinks, and [[https://github.com/org-roam/org-roam-ui][org-roam-ui]] for the graph,
- maps of content, a graph review and note tasks in the agenda, see
  [[file:../../../docs/org-roam-guide.org][the roam guide]],
- mind maps through graphviz, exports to GFM, Pandoc and LaTeX, and a
  writing mode.

* Keybindings
Everything is in ~SPC n SPC~ (~+notes/menu~), which shows how many items are
waiting in the inbox. Its keys are the leader's: ~d~ the documents as
under ~SPC n d~, ~c~ the captures, ~r~ roam as under ~SPC n r~, ~a~ the
agenda views of ~SPC o a~, and ~h~ ~g~ ~G~ ~p~ ~u~ ~P~ ~B~ as on ~SPC n~ itself.
A key ~SPC n~ gives another command is left to it: export is ~E~, ~SPC n e~
being org-noter, and org-ql find is ~a /~, since ~q~, as a key's last,
closes the menu.

** Roam
[[file:../../../docs/org-roam-guide.org][The guide]] says how to work with the graph day to day; ~SPC n r ?~ opens
it. A note is one of thirteen kinds, each a set of
headings that say what to write: concept (in one sentence, how it works,
example, where it bites), solution (symptom, cause, fix, how to verify,
applies to), howto (when, steps, gotchas), hardware (a board or part:
pinout, toolchain, gotchas), reference (a source: key points, quotes, my
take), question, project (a dashboard, goal, completion criteria, next
actions, decisions, progress, with the repository and the kit in its
head), person, meeting, and for work and study, course (~u~), lecture
(~l~), case study (~k~) and design doc (~D~). Concept, solution, howto,
hardware and question ask for their subject directory under
=resources/wiki/=, a new one when you type a name that is not there and
press ~M-RET~; a reference goes to =resources/sources/manuals/= with its URL in
=ROAM_REFS=, a project to =projects/=, a person to
=resources/wiki/people/=, a meeting to =capture/meetings/=, apart from the
dailies in =capture/journal/= so that the next and previous daily
(~SPC n r d f~, ~SPC n r d b~) are days only. Where the four others go is
in [[*Work and study][Work and study]].
~SPC n r n~ picks one; ~c n~ and ~c m~ in the menu make a concept and a
meeting straight away.

|-------------+-----------------------------------------------------|

| ~SPC n r N~   | rename this note, its file and the links to it      |

| ~SPC n r S~   | the starred notes                                   |
| ~SPC n h~     | the notes layout: tree and outline, note, roam buffer |
| ~SPC n r d n~ | write today's daily note                            |
| ~SPC m m e~   | extract this heading into its own note              |

The roam buffer shows, under the backlinks and the references, the
unlinked mentions: the lines elsewhere in the vault that name the note's
title or an alias without linking to it, the links still to be made.
They are a ripgrep search with PCRE2, which ~doom doctor~ checks for.

With the cursor on an =id:= or =roam:= link, the echo area says what it
points to: the note's title, its tags as =#tag= and its path in the vault.
~SPC c H~ then shows the note itself in a popup, its first 20 lines without
the property drawer and the =#+= keywords; a heading's note shows its
subtree. Read once per change of the file.

~SPC n r N~ renames the note at point: the =#+title= of a file, the text
of a heading that is a node, its keyword, priority and tags kept. A file
named for the old title, =signal_integrity.org= or a meeting's
=20261031-signal_integrity.org=, takes the new one; any other name, a
daily note's, a project's =index.org=, a paper's citekey, stays, and so
does one whose new name is taken, which the message says. Every =id:=
link described by exactly the old title then reads the new one, in open
buffers and closed files alike; a description of your own, =SI=, is left
alone, and a buffer with unsaved changes is edited but not saved. Editing
the =#+title= and saving does the same.

A starred note carries the tag =starred=: ~SPC m m o s~ puts it in the
=#+filetags= of a file, or on the heading of a heading node, and takes it
off again; the star counts once the note is saved. ~SPC n r S~ lists the
starred files and the starred headings of files that are not, a starred
file's headings being starred through it already.

~SPC n r t~ lists every tag with how many notes carry it, most used first,
then the notes of the one picked. A heading that is a note counts, and so
do the tags it inherits from its file, as org-roam keeps them; ~SPC n r m~
writes the same set as a map.

~SPC n h~ lays the notes out in a workspace of their own, =notes=: the
side bar at the left, the vault's tree above the note's outline (the
sidebar module's Explorer, pinned to the vault there), the note, and at
the right the roam buffer, which follows the note. It shows the vault
file used last, or today's daily note; ~SPC n h~ there again puts the
side bar and the roam buffer away and leaves the note. The other
workspaces keep their own windows; the side bar shows each one's project.

A picture belongs to the note it is in: ~SPC m a p~ pastes the one on the
clipboard (=pngpaste= on a Mac, which ~doom doctor~ asks for), ~SPC m a c~
takes a screenshot, and a picture file dropped on the note is copied in,
with no question. Each goes into the note's folder under =.attach/=, named
by the note's ID, and an =attachment:= link to it is put where the cursor
is; under a heading with no ID it is the note's folder, and the heading
stays as it was, not a note of its own. A note opens with the pictures
its links name shown, as Org shows them: a link with no description, of
any kind Org draws, an =attachment:=, a =file:= or a plain =./img/a.png=, 500
pixels wide unless an =#+attr_org: :width= says otherwise. A note whose
links name no picture skips that work; =#+startup: nolinkpreviews= keeps
them off. A diagram or picture of no one note lives in =assets/=. Both
folders are committed with the notes.

A callout is a block of one of five kinds, ~+notes-callout-types~: note,
tip, important, warning, caution, with a title after the kind if wanted,
=#+begin_warning Careful= ... =#+end_warning=. Its first and last lines
are drawn in the kind's face, ~+notes-callout-warning~ and the others,
each a face of the theme in bold; the text inside is the note's. ~C-c C-,~
then ~N~ ~T~ ~I~ ~W~ ~X~ inserts one; the lower case ~n~ stays
org-re-reveal's speaker notes. HTML export gives =<div class="warning">=.

A task written inside a note reaches the agenda: before an agenda or a
refile the inbox, =projects/=, =areas/= and the journal
(=capture/journal/=) are scanned for open keywords (the ones in
~org-todo-keywords~) and those files join ~+notes-agenda-base-files~ in
~org-agenda-files~; the dashboard's Tasks group shows them. A task typed
into a daily note stays in view, whatever its date, until it is refiled
into its project. =archives/=, sources, drafts and knowledge pages are
not scanned, so a code example never becomes a task. A view that binds its
own file list, the inbox, keeps it. Recent daily notes are agenda files
for their dates but not refile targets. =.private/=, =.cache/= and =.git/=
never become nodes.

The graph's database never holds Emacs on the whole vault. A full sync
runs in a background Emacs (=emacs --batch=, under =nice= at
~+core-build-niceness~) given what this one writes a note with: the
variables of ~+notes-roam-build-variables~, the link types, and the
module's rules (the folders above, a heading tagged =:noroam:= or a
card no node, a live table's links none of the note's). It runs once a
session, a second after org-roam loads, for what changed while Emacs
was not running; on ~SPC n r s~ (~SPC u SPC n r s~ builds it anew); after
~SPC n G~ pulls. It writes a copy of the database, which then takes its
place; a note saved meanwhile is written into the copy first, so no
save is lost and the two Emacs never write one file. A save still
updates its own note at once, 85 to 105 ms for most notes of a 1593
note vault, about half of it the disk. On a copy of that vault the
first build held Emacs 85 to 173 s and the session's sync 2.2 to 2.4 s;
now neither holds it at all, the first build taking 30 s in the
background and the sync 3. Until a first build is done, the finder, the
tags, the starred notes, a map, the review, a live list and the menu say
it is being built and how far, rather than show a vault with no notes;
renaming waits for it, and a title changed meanwhile renames at the
first save after it. When a build fails, the database stays as it was
and the message names the buffer =*roam build*=.

Cards are headings tagged =:fc:= in the notes themselves, scheduled through
their own properties; the review reads the cards of the whole vault. The
card dashboard, ~SPC n P~, asks which cards, each choice said in words,
and opens in a popup that ~q~ and =ESC= close; there ~r~ reviews them, ~n~
and ~p~ move between its sections and ~TAB~ opens or closes one. The
bibliography is =research/academic/references.bib= under the library,
~+notes-library-dir~, with the PDFs in =research/academic/papers/= there;
nothing here creates either, and ~doom doctor~ says when the =.bib= is
missing. citar writes its notes into the vault as
=resources/sources/papers/<citekey>.org=, so a cited paper and the note
about it are the same thing. The vault is a git repository, made
by ~SPC n d b~, and commits everything in it after ~+notes-commit-idle~
seconds of idle time and when Emacs exits, never while a rebase or merge
is waiting, and says so when a commit fails. ~SPC n G~ pulls and pushes in
the background; a conflict stops it with a message and magit finishes it.
The org-roam database (=org-roam-knowledge.db= under Doom's cache) and the
card review log are caches outside the vault, so only the files travel
between machines; the database is synced in the background after the
pull, so the finder knows the notes the other machine wrote.

Maps live in =resources/collections/tags/=. A map is a note of its own, so
it shows in the graph; only the list between =# BEGIN MAP= and =# END MAP=
is regenerated. Authored subject indexes and collections are other files
and are never regenerated. ~SPC n r m~ opens the map in a popup on the
right, which =ESC= closes; a tag no note carries asks before it makes an
empty map.

* Work and study
Courses, case studies and a project's design work are notes of the graph
like any other, with live tables in them that say what is open.

** Courses and lectures
~SPC n r n u~ makes a course, =areas/university/<course>/index.org=,
active and tagged =course=: an overview (teacher, term, exam), its
timetable, its assignments and exams, and live tables of its lectures,
its board, what is due in the next two weeks and its case studies. A
class is a repeating date in angle brackets under Timetable,
=<2026-11-03 Tue 10:00-12:00 +1w>=; a course's index is an agenda file
and a refile target, so its classes show in every agenda. A course whose
=STATUS= is paused, archived or completed is no longer added to them nor
offered for a capture; as with a project, a task still open in it keeps
it in the agenda.

~SPC n r n l~ makes a lecture in its course's =lectures/=,
=YYYYMMDD-<title>.org=, tagged =lecture=: a first line linking to the
course, then Summary, Notes, Questions and Cards. From a note of a course
it takes that course; from anywhere else it asks which. ~SPC X e~ puts an
assignment or an exam under the course's Assignments and exams, tagged
with its kind and with a deadline. ~SPC n u~ reviews the cards of the
course the note belongs to, and only those; from any other note it asks
which course.

University, =areas/university/index.org= (~SPC n d u~), lists the
courses and what is due in the next two weeks. ~SPC o a u~ is the
University agenda: fourteen days of classes and deadlines, then the open
tasks, a group per course, named for it; a task of University itself,
or of a course no longer active, is under University.

** Case studies
~SPC n r n k~ makes a case study in =resources/case-studies/=, tagged
=case_study=, with Context, Problem, Analysis, Options, Decision,
Outcome, Lessons and Sources. Its first line, =For:=, links to the course
or project it is for, picked when it is made, or to nothing; that course
or project lists it in its Case studies table. Its tasks stay out of the
agenda, as everything in =resources/= does.

** Projects: the dashboard, design and decisions
A project's index opens with its Dashboard: its board, its design
documents, its decisions and its case studies, all live. Both ways of
making a project, ~SPC X P~ and ~SPC n r n p~, write it and mark the
project active. The project index, =projects/index.org=, lists the active
projects.

~SPC n r n D~ makes a design document in the project's =design/=, a note
of its own, with Context, Goals, Non-goals, Requirements, Design,
Alternatives, Risks and Open questions; its =STATUS= starts at draft and
goes to review and accepted by hand. ~SPC X d~ puts a decision under the
project's Decisions: a heading tagged =decision=, with an ID, so it is a
note of the graph, a =STATUS= (accepted or proposed), the =DATE= and the
lines Context, Decision, Consequences and Alternatives. A decision
replaced by another is marked superseded by hand, with a link to the
one that replaces it. Both find the project as ~pt~ does; with none, the
decision goes to the inbox and the design document is refused.

A course, a lecture, a case study and a design document are always new
notes: picking an existing note in the finder is refused, since its file
would get the template. To make a note whose title an existing note has
already, type the title and press ~M-RET~, which takes it as typed; when
its file would be one that exists, the same course, case study or design
document, or a lecture of that title the same day, it is refused too.

** Live tables
Three Org dynamic blocks of this module's own: =notes-query=, the
headings an Org QL query finds, =notes-list=, notes of the graph, and
=notes-board=, tasks in columns by state.

#+begin_example
#+BEGIN: notes-query :from folder :query "todo: deadline:to=14" :columns (deadline todo heading file) :sort deadline
#+END:
#+end_example

| Parameter  | Block        | What                                          |
|------------+--------------+-----------------------------------------------|
| =:from=      | all          | =file=, =folder= (default), =agenda=, ="DIR/"=, =vault= |
| =:query=     | query, board | an Org QL string query, never Lisp            |
| =:columns=   | query, list  | the columns                                   |
| =:sort=      | all          | the order                                     |
| =:take=      | query, list  | at most this many rows                        |
| =:tags=      | list         | =("a" "b")=: notes that carry every one         |
| =:links-to=  | list         | =this=: notes with an =id:= link to this one      |
| =:property=  | list         | =("STATUS" "active")=                           |
| =:level=     | list         | =file= (default), =heading= or =any=                |
| =:states=    | board        | the columns, ~+notes-board-states~              |
| =:done-days= | board        | days a finished task stays, or =all=            |

=:from folder= is this note's folder and those below it, =agenda= the
agenda files, a ="DIR/"= a folder of the vault with those below it, and
=vault= the whole vault, for a list only. =notes-query= needs a =:query=;
a board's is joined with its states by "and". A query's columns are
=todo= =priority= =heading= =tags= =deadline= =scheduled= =closed= =file=,
=todo heading deadline file= by default; a list's are =title= =tags=
=file= =modified= =created=, =title= by default; either takes
=(property "NAME")=, and any column as =(COLUMN "Header")=. A query and a
board sort by Org QL's =deadline= =scheduled= =closed= =priority= =todo=
=date= and =reverse=, else in the files' order; a list by =title=, the
default, or =modified= or =created=, newest first. A list's =:tags= count
the tags a note inherits too.

~SPC m Q q~, ~l~ and ~b~ insert one on the line below, or below a
heading's dates and drawers when point is on it, reading this note's
folder (at the vault's root a query or a board reads the agenda files
and a list the vault), and ~C-c C-x x~ offers them with Org's others. A
note's tables are written again when it is shown and when it is saved,
~SPC m Q u~ or ~C-c C-c~ on one at any time. Showing a note does not mark
it changed, so one only looked at keeps its old tables on disk until the
next edit and save; ~u~ after opening may bring the old ones back. A
note opened in the background, by the agenda or a query, is not written.
Other dynamic blocks, a clock table or an =org-ql= block, are left as
they are.

A heading with an ID is linked by its ID, one without by its file and
heading text, or by its file alone when the text holds =|= or an active
date. A =|= in a cell is written =\vert{}=, and an active date inactive,
so a table never puts anything in the agenda. =notes-list= reads the
database, so a note is listed once saved. A query or a board over the
whole vault would open every note, so =:from folder= at the vault's root
and =:from vault= give a line saying so instead, as does any block that
cannot be written, which keeps the note's other tables and its save
going. Showing, saving and ~SPC m Q u~ leave alone a block quoted in a
source, example, export, comment or verse block or a LaTeX environment,
each closed by its own end line before the next heading (one not closed
there quotes nothing), and a block with no =#+END:= of its own before
the next heading or =#+BEGIN:= line, which never takes another's;
~C-c C-c~ is Org's own and takes the next =#+END:= it finds, so type the
=#+END:= first.

What a table writes is the module's, not the note's, as Obsidian leaves
Dataview's out: org-roam's database keeps only the links and citations
written outside the three blocks, so the backlinks and reflinks, the
forward links, the graph, ~SPC n r v~ and a list's =:links-to= see none
of a table's, and the unlinked mentions skip its lines. A note only
tables list counts in ~SPC n r v~ as linked from nowhere, and a note
whose only links are its tables as linking nowhere. A block's
=#+BEGIN:= line is the note's, and other dynamic blocks and a block
with no =#+END:= of its own are read as before. A database indexed
before this keeps a table's links and citations until its note is next
changed and saved; ~SPC u SPC n r s~ rebuilds it whole.

** Boards
A board has a column per state, ~+notes-board-states~ (TODO NEXT STRT WAIT
DONE), and a card per task; a finished one stays
~+notes-board-done-days~ (14) after it was closed. ~S-<right>~ or ~C-S-l~
on a card sets its task to the next column's state, ~S-<left>~ or
~C-S-h~ to the one before, through ~org-todo~, so the log lines, the notes
WAIT asks for and the dependencies work as ever, and a repeating task
comes back with its dates moved on. The task's file is
saved when it had no other change, once its log note is in when it asks
for one; one with unsaved changes is left so, and the message says it.
A card is found by its ID, else by the one heading of its file that reads
the same; two that read the same are refused, and ~org-id-get-create~ on
one of them gives it an ID. Anywhere else the keys do what Org does.

* Workflow
1. Capture into the inbox, from anywhere, or straight into the project
   that owns the task.
2. Empty it: refile with ~SPC m r r~ into its project, set NEXT, give it a date.
3. Work from ~SPC o a x~, write the day down in the daily note.
4. Review weekly with ~SPC o a w~.
5. What you want to keep goes to roam: promote a heading with ~SPC m m e~
   into its subject directory, link it with ~SPC n r i~, tag it, then
   rebuild its map with ~SPC n r m~.
6. When a project is done or paused, move it under =archives/projects/=
   with its ID, review its open tasks rather than marking them done, and
   leave its reusable notes where they are.

Work notes need nothing of their own: a project per outcome, worked from
its dashboard, a meeting note per meeting (~SPC n r n m~), a person note
per colleague (~SPC n r n P~), and the day in the daily note.

After a change here, ~bin/check-config~ is the check to run. Importing a
source is not hardware verification, and indexing never runs an Org
source block.

* Spelling and style
Words are checked as you type against British English, which is how
the notes are spelt, and American, which code and quotes bring in, and
against =dictionary.pws= in this module: the words of this config and
its tools, config, keymap, clangd, magit, gathered from the notes, the
READMEs and the cheat sheet, where aspell alone marked 300 of them. ~zg~
adds a word to it and ~z=~ corrects one. A possessive is checked as its
word, so config's passes with config. The tags, dates and labels
org-modern draws are not checked, as the code, the links and the
verbatim are not. Italian is left to LanguageTool below: spell-fu keeps
every form of every word in memory, and Italian has twenty million.

writegood, which marks the passive voice, a list of vague words and a
word said twice, is off: it made 116 marks in the notes and none was an
error, and it makes org's own rules ignore case, so a heading called
Done broke the fontification of =reading.org=. LanguageTool, below,
reads the style when asked.

* Grammar
~SPC n w c~ runs LanguageTool over the buffer, ~SPC n w w~ says what is
wrong where the cursor is, ~SPC n w f~ walks the buffer correcting, and
~SPC n w d~ clears the marks. ~langtool-default-language~ is ~auto~ here
rather than Doom's "en-US", since the notes are written in two
languages and the tool detects which; ~langtool-mother-tongue~ is "it",
which is what turns on the false-friend rules.

The classpath is this module's: Doom points it at
=/usr/share/java/languagetool=, which on openSUSE holds three jars
without the =libs/= beside them, so a check dies on a missing class. The
module looks for the directory that holds the whole set and puts its
=libs= on the classpath too. ~SPC h r d~ says so when the jars or the java
that runs them are missing.

* Code blocks and LaTeX
A code block in markdown or org is coloured by the mode of its
language, run in a hidden buffer over the whole block at each key typed
in it. The block gets the mode a file of that language opens in:
markdown took a tree-sitter mode only when that mode was in
~auto-mode-alist~, and org never did, so a C block went to cc-mode.
Typing in a 230 line C block of the blog takes 22 ms instead of 35, in a
10 line one 6 ms, in prose 4; half the blocks there are five lines. The
whole block is still coloured again at each key: that is how
markdown-mode does it. The mode for a language is looked up once a
session, not for every block at every key.

markdown-mode tries every =*= and =_= of a line as the start of an
italic or a bold, and asked for each whether it sat in inline code by
matching the code of its paragraph again from the start. A file of long
lines full of names like =espressif__mdns= took up to two seconds a line
moved; the code of a paragraph is found once now, 64 s to 1.3 s for the
whole of a 160 KB file, with the same colours.

Org looks for LaTeX to colour from the text being coloured on to the
next fragment, which in a file with few is its end, at every key and for
every heading on screen. It stops now ~+notes-latex-reach~ characters
past that text, room for a fragment that starts in it to end. The cheat
sheet opens in 0.3 s instead of 1.4 and takes 5 ms a key instead of 19,
and its colours are the same.

* Configuration
- ~+core-notes-dir~, the vault, which is ~org-directory~ and, through
  ~+notes-knowledge-dir~ (its default), ~org-roam-directory~. The
  documents, the inbox and the agenda take the two for one folder. Set in
  =init.el=, before any module or ~doom doctor~ reads it; unset, it is
  =~/org=. A folder that is missing is made when org loads, with
  ~+notes-knowledge-directories~ inside; ~doom doctor~ says when the vault
  is missing or not a git repository.
- ~+notes-documents~, the seven documents, and ~+notes-templates-dir~,
  where their templates are.
- ~+notes-roam-head~, the header every roam note starts with;
  ~+notes-daily-name~ and ~+notes-daily-head~, a daily note's file name
  and first lines.
- ~+notes-library-dir~, the library of books and papers, set in
  =init.el= (=~/projects/personal/knowledge_base/= here and by default);
  ~+notes-bibliography~ (=research/academic/references.bib= under it),
  with ~citar-library-paths~ its =research/academic/papers=.
- ~+notes-commit-idle~ (600).
- ~+notes-board-states~ (TODO NEXT STRT WAIT DONE), a board's columns
  when it names none, and ~+notes-board-done-days~ (14), how many days a
  finished task stays on a board.
- ~+notes-latex-reach~ (4096), how far past the text being coloured org
  looks for LaTeX.
- ~+notes-roam-build-variables~, what the background build of the
  database takes from this Emacs: a variable that changes what a note
  writes into the database belongs there.
- The files: =config.el= (documents, the workflow block, the commit
  timer, keys), =+capture.el=, =+agenda.el=, =+roam.el=, =+study.el=
  (citar, org-fc, transclusion), =+export.el=; =autoload/capture.el=
  resolves the inbox, the owning project and the course for every
  capture; =autoload/query.el= writes the live tables and moves cards;
  =autoload/roam-db.el= builds the database in the background.
- TODO keywords: Doom's, plus NEXT. Tags: ~org-tag-alist~.

* For other modules
=autoload/write.el= writes into the notes without a capture, in the shape
the templates give: ~+notes-daily-file~ (today's note, made when
missing), ~+notes-append-daily~ (an entry under one of its headings),
~+notes-add-inbox-todo~ (a task in the knowledge inbox, with who wrote
it), ~+notes-new-draft~ (a note in waiting under =capture/drafts/=, tagged
=:draft:=). The ai module's tools go through these, so what Claude leaves
looks like what you write.

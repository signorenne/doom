#+title:    :private notes
#+subtitle: documents, capture, agenda and roam

* Description
Everything written lives in one vault, ~+core-notes-dir~, =~/notes= on
this machine (set in =init.el=): org notes, PlantUML diagrams and
pictures. The vault is ~org-directory~ and ~org-roam-directory~ at once,
one Org-roam graph where Zettelkasten knowledge and PARA work meet, and
one git repository that commits itself. Books and papers are a library
apart, ~+notes-library-dir~, which only citar reads.

- the inbox =inbox.org= and one =projects/<slug>/index.org= per
  bounded outcome, with Goal, Completion criteria, Next actions, Decisions,
  Progress and Knowledge and sources,
- six documents, each a node of the graph, created from =templates/org=:
  the inbox, the project index, someday, reading, snippets and habits.
  See ~+notes-documents~,
- captures that write into the inbox or the owning project, including the
  region as a code snippet and a bug report with a link back to the line,
- an [[https://github.com/alphapapa/org-super-agenda][org-super-agenda]] dashboard and a weekly review, plus [[https://github.com/alphapapa/org-ql][org-ql]] queries,
- org-roam for lasting notes, with dailies as the journal, [[https://github.com/jgru/consult-org-roam][consult-org-roam]]
  for search and backlinks, and [[https://github.com/org-roam/org-roam-ui][org-roam-ui]] for the graph,
- maps of content, a graph review and note tasks in the agenda, see
  [[file:../../../docs/org-roam-guide.org][the roam guide]],
- mind maps through graphviz, exports to GFM, Pandoc and LaTeX, and a
  writing mode.

* Keybindings
Everything is in ~SPC n SPC~ (~+notes/menu~), which shows how many items are
waiting in the inbox. Its keys are the leader's: ~d~ the documents as
under ~SPC n d~, ~c~ the captures, ~r~ roam as under ~SPC n r~, ~a~ the
agenda views of ~SPC o a~, and ~h~ ~g~ ~G~ ~p~ ~P~ ~B~ as on ~SPC n~ itself.

The inbox and someday are at the vault's root, the project index is
=projects/index.org=, reading and snippets are in =resources/=, the
habits in =areas/=. The inbox and the habits are in the agenda; someday

Refile each inbox entry once, into the project that owns it. ~P~ creates or
reuses the project by its outcome title; roam's ~p~ uses the same
=projects/<slug>/index.org=. ~pt~ and ~ot~ find the owning project from an
explicit buffer-local ~+notes-project-file~ or the project whose
=REPOSITORY= names this code repository; several matches, or none, ask for
a project or the inbox. A code repository is not a project by itself, and
no capture invents one.

** Roam
[[file:../../../docs/org-roam-guide.org][The guide]] says how to work with the graph day to day; ~SPC n r ?~ opens
it. A note is one of nine kinds, each a set of
headings that say what to write: concept (in one sentence, how it works,
example, where it bites), solution (symptom, cause, fix, how to verify,
applies to), howto (when, steps, gotchas), hardware (a board or part:
pinout, toolchain, gotchas), reference (a source: key points, quotes, my
take), question, project (goal, completion criteria, next actions,
decisions, progress, with the repository and the kit in its head),
person, meeting. Concept, solution, howto, hardware and question ask for
their subject directory under =resources/wiki/=; a reference goes to
=resources/sources/manuals/= with its URL in =ROAM_REFS=, a project to
=projects/=, a person to =resources/wiki/people/=, a meeting to
=capture/meetings/=, apart from the dailies in =capture/journal/= so that
the next and previous daily (~SPC n r d f~, ~SPC n r d b~) are days only.
~SPC n r n~ picks one; ~c n~ and ~c m~ in the menu make a concept and a
meeting straight away.

| Key         | What it does                                   |
|-------------+------------------------------------------------|
| ~SPC n r f~   | find or create a node, ~i~ links to one          |
| ~SPC n r n~   | new note, one of the nine kinds                |
| ~SPC n r /~   | search the notes, ~B~ backlinks, ~L~ forward links |
| ~SPC n r r~   | the roam buffer: backlinks and unlinked mentions |
| ~SPC c H~     | on a link, the linked note's first lines in a popup |
| ~SPC n r N~   | rename this note, its file and the links to it   |
| ~SPC m m o s~ | star this note, or unstar it                     |
| ~SPC n r S~   | the starred notes                                |
| ~SPC n h~     | the notes layout: tree, note, roam buffer, outline |
| ~SPC n r d n~ | write today's daily note                       |
| ~SPC m m e~   | extract this heading into its own note         |
| ~SPC n r t~   | the tags, how many notes each, then their notes  |
| ~SPC n r m~   | build the map of a tag                         |
| ~SPC n r v~   | review the notes that went nowhere             |
| ~SPC n r h~   | which notes carry tasks                        |
| ~SPC n r u~   | the graph in a browser                         |

The roam buffer shows, under the backlinks and the references, the
unlinked mentions: the lines elsewhere in the vault that name the note's
title or an alias without linking to it, the links still to be made.
They are a ripgrep search with PCRE2, which ~doom doctor~ checks for.

With the cursor on an =id:= or =roam:= link, the echo area says what it
points to: the note's title, its tags as =#tag= and its path in the vault.
~SPC c H~ then shows the note itself in a popup, its first 20 lines without
the property drawer and the =#+= keywords; a heading's note shows its
subtree. Read once per change of the file.

~SPC n r N~ renames the note at point: the =#+title= of a file, the text
of a heading that is a node, its keyword, priority and tags kept. A file
named for the old title, =signal_integrity.org= or a meeting's
=20261031-signal_integrity.org=, takes the new one; any other name, a
daily note's, a project's =index.org=, a paper's citekey, stays, and so
does one whose new name is taken, which the message says. Every =id:=
link described by exactly the old title then reads the new one, in open
buffers and closed files alike; a description of your own, =SI=, is left
alone, and a buffer with unsaved changes is edited but not saved. Editing
the =#+title= and saving does the same.

A starred note carries the tag =starred=: ~SPC m m o s~ puts it in the
=#+filetags= of a file, or on the heading of a heading node, and takes it
off again; the star counts once the note is saved. ~SPC n r S~ lists the
starred files and the starred headings of files that are not, a starred
file's headings being starred through it already.

~SPC n r t~ lists every tag with how many notes carry it, most used first,
then the notes of the one picked. A heading that is a note counts, and so
do the tags it inherits from its file, as org-roam keeps them; ~SPC n r m~
writes the same set as a map.

~SPC n h~ lays the notes out in a workspace of their own, =notes=: the
vault's file tree at the left, the note, and at the right the roam buffer,
which follows the note, above its outline. It shows the vault file used
last, or today's daily note; ~SPC n h~ there again puts the three panels
away and leaves the note. The other workspaces keep their own windows;
switching to one with no outline in sight pauses the outline's updates,
and switching back resumes them.

A picture belongs to the note it is in: ~SPC m a p~ pastes the one on the
clipboard (=pngpaste= on a Mac, which ~doom doctor~ asks for), ~SPC m a c~
takes a screenshot, and a picture file dropped on the note is copied in,
with no question. Each goes into the note's folder under =.attach/=, named
by the note's ID, and an =attachment:= link to it is put where the cursor
is; under a heading with no ID it is the note's folder, and the heading
stays as it was, not a note of its own. A note opens with the pictures
its links name shown, as Org shows them: a link with no description, of
any kind Org draws, an =attachment:=, a =file:= or a plain =./img/a.png=, 500
pixels wide unless an =#+attr_org: :width= says otherwise. A note whose
links name no picture skips that work; =#+startup: nolinkpreviews= keeps
them off. A diagram or picture of no one note lives in =assets/=. Both
folders are committed with the notes.

A task written inside a note reaches the agenda: before an agenda or a
refile the inbox, =projects/=, =areas/= and the journal
(=capture/journal/=) are scanned for open keywords (the ones in
~org-todo-keywords~) and those files join ~+notes-agenda-base-files~ in
~org-agenda-files~; the dashboard's Tasks group shows them. A task typed
into a daily note stays in view, whatever its date, until it is refiled
into its project. =archives/=, sources, drafts and knowledge pages are
not scanned, so a code example never becomes a task. A view that binds its
own file list, the inbox, keeps it. Recent daily notes are agenda files
for their dates but not refile targets. =.private/=, =.cache/= and =.git/=
never become nodes.

** Studying, sources and keeping it
| Key         | What it does                                       |
|-------------+----------------------------------------------------|
| ~SPC n p~     | review the flashcards due, ~P~ the dashboard         |
| ~SPC m F n~   | turn this heading into a card, ~c~ blanks out a part |
| ~SPC n B~     | the bibliography, ~b~ the note on an entry           |
| ~SPC n d P~   | register org-protocol, then use the bookmarklets   |
| ~SPC m N n~   | transclude the link at point, ~A~ show them all      |
| ~SPC n g~     | commit the notes, ~G~ syncs with the remote          |
| ~SPC n SPC H~ | what changed in the notes, ~V~ makes them a repository |

Cards are headings tagged =:fc:= in the notes themselves, scheduled through
their own properties; the review reads the cards of the whole vault. The
bibliography is =research/academic/references.bib= under the library,
~+notes-library-dir~, with the PDFs in =research/academic/papers/= there;
nothing here creates either, and ~doom doctor~ says when the =.bib= is
missing. citar writes its notes into the vault as
=resources/sources/papers/<citekey>.org=, so a cited paper and the note
about it are the same thing. The vault is a git repository, made
by ~SPC n d b~, and commits everything in it after ~+notes-commit-idle~
seconds of idle time and when Emacs exits, never while a rebase or merge
is waiting, and says so when a commit fails. ~SPC n G~ pulls and pushes in
the background; a conflict stops it with a message and magit finishes it.
The org-roam database (=org-roam-knowledge.db= under Doom's cache) and the
card review log are caches outside the vault, so only the files travel
between machines; the database is rebuilt after the pull, so the finder
knows the notes the other machine wrote.

Maps live in =resources/collections/tags/=. A map is a note of its own, so
it shows in the graph; only the list between =# BEGIN MAP= and =# END MAP=
is regenerated. Authored subject indexes and collections are other files
and are never regenerated.

* Workflow
1. Capture into the inbox, from anywhere, or straight into the project
   that owns the task.
2. Empty it: refile with ~SPC m r r~ into its project, set NEXT, give it a date.
3. Work from ~SPC o a x~, write the day down in the daily note.
4. Review weekly with ~SPC o a w~.
5. What you want to keep goes to roam: promote a heading with ~SPC m m e~
   into its subject directory, link it with ~SPC n r i~, tag it, then
   rebuild its map with ~SPC n r m~.
6. When a project is done or paused, move it under =archives/projects/=
   with its ID, review its open tasks rather than marking them done, and
   leave its reusable notes where they are.

After a change here, ~bin/check-config~ is the check to run. Importing a
source is not hardware verification, and indexing never runs an Org
source block.

* Spelling and style
Words are checked as you type against British English, which is how
the notes are spelt, and American, which code and quotes bring in, and
against =dictionary.pws= in this module: the words of this config and
its tools, config, keymap, clangd, magit, gathered from the notes, the
READMEs and the cheat sheet, where aspell alone marked 300 of them. ~zg~
adds a word to it and ~z=~ corrects one. A possessive is checked as its
word, so config's passes with config. The tags, dates and labels
org-modern draws are not checked, as the code, the links and the
verbatim are not. Italian is left to LanguageTool below: spell-fu keeps
every form of every word in memory, and Italian has twenty million.

writegood, which marks the passive voice, a list of vague words and a
word said twice, is off: it made 116 marks in the notes and none was an
error, and it makes org's own rules ignore case, so a heading called
Done broke the fontification of =reading.org=. LanguageTool, below,
reads the style when asked.

* Grammar
~SPC n w c~ runs LanguageTool over the buffer, ~SPC n w w~ says what is
wrong where the cursor is, ~SPC n w f~ walks the buffer correcting, and
~SPC n w d~ clears the marks. ~langtool-default-language~ is ~auto~ here
rather than Doom's "en-US", since the notes are written in two
languages and the tool detects which; ~langtool-mother-tongue~ is "it",
which is what turns on the false-friend rules.

The classpath is this module's: Doom points it at
=/usr/share/java/languagetool=, which on openSUSE holds three jars
without the =libs/= beside them, so a check dies on a missing class. The
module looks for the directory that holds the whole set and puts its
=libs= on the classpath too. ~SPC h r d~ says so when the jars or the java
that runs them are missing.

* Code blocks and LaTeX
A code block in markdown or org is coloured by the mode of its
language, run in a hidden buffer over the whole block at each key typed
in it. The block gets the mode a file of that language opens in:
markdown took a tree-sitter mode only when that mode was in
~auto-mode-alist~, and org never did, so a C block went to cc-mode.
Typing in a 230 line C block of the blog takes 22 ms instead of 35, in a
10 line one 6 ms, in prose 4; half the blocks there are five lines. The
whole block is still coloured again at each key: that is how
markdown-mode does it. The mode for a language is looked up once a
session, not for every block at every key.

markdown-mode tries every =*= and =_= of a line as the start of an
italic or a bold, and asked for each whether it sat in inline code by
matching the code of its paragraph again from the start. A file of long
lines full of names like =espressif__mdns= took up to two seconds a line
moved; the code of a paragraph is found once now, 64 s to 1.3 s for the
whole of a 160 KB file, with the same colours.

Org looks for LaTeX to colour from the text being coloured on to the
next fragment, which in a file with few is its end, at every key and for
every heading on screen. It stops now ~+notes-latex-reach~ characters
past that text, room for a fragment that starts in it to end. The cheat
sheet opens in 0.3 s instead of 1.4 and takes 5 ms a key instead of 19,
and its colours are the same.

* Configuration
- ~+core-notes-dir~, the vault, which is ~org-directory~ and, through
  ~+notes-knowledge-dir~ (its default), ~org-roam-directory~. The
  documents, the inbox and the agenda take the two for one folder. Set in
  =init.el=, before any module or ~doom doctor~ reads it; unset, it is
  =~/org=. A folder that is missing is made when org loads, with
  ~+notes-knowledge-directories~ inside; ~doom doctor~ says when the vault
  is missing or not a git repository.
- ~+notes-documents~, the six documents, and ~+notes-templates-dir~, where
  their templates are.
- ~+notes-roam-head~, the header every roam note starts with;
  ~+notes-daily-name~ and ~+notes-daily-head~, a daily note's file name
  and first lines.
- ~+notes-library-dir~, the library of books and papers, set in
  =init.el= (=~/projects/personal/knowledge_base/= here and by default);
  ~+notes-bibliography~ (=research/academic/references.bib= under it),
  with ~citar-library-paths~ its =research/academic/papers=.
- ~+notes-commit-idle~ (600).
- ~+notes-latex-reach~ (4096), how far past the text being coloured org
  looks for LaTeX.
- The files: =config.el= (documents, the workflow block, the commit
  timer, keys), =+capture.el=, =+agenda.el=, =+roam.el=, =+study.el=
  (citar, org-fc, transclusion), =+export.el=; =autoload/capture.el=
  resolves the inbox and the owning project for every capture.
- TODO keywords: Doom's, plus NEXT. Tags: ~org-tag-alist~.

* For other modules
=autoload/write.el= writes into the notes without a capture, in the shape
the templates give: ~+notes-daily-file~ (today's note, made when
missing), ~+notes-append-daily~ (an entry under one of its headings),
~+notes-add-inbox-todo~ (a task in the knowledge inbox, with who wrote
it), ~+notes-new-draft~ (a note in waiting under =capture/drafts/=, tagged
=:draft:=). The ai module's tools go through these, so what Claude leaves
looks like what you write.

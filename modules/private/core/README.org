#+title:    :private core
#+subtitle: environment, defaults and maintenance

* Description
The small global things:

- environment: tree-sitter grammars install themselves, =~/.local/bin= stays
  on =exec-path=, and an Emacs server runs so =emacsclient= works: one
  Emacs for everything, a daemon started at login (=M-x
  +core/install-daemon=, a launchd agent on macOS, Emacs's systemd unit
  on Linux) whose windows Emacs Client.app opens; Emacs.app opened by
  itself, from the Dock or Finder, hands its files to that daemon and
  quits (=EMACS_SERVER_NAME= set to an unused name keeps one of its own),
- at rest on a name in a file with a language server, the echo area
  shows its declaration as code, return type, name and parameters,
  =void debug_push_event(event_type const type, ...)=, and in gray what
  the line does not say: the type an =auto= stands for, a constant's or
  an enumerator's value, a struct's or a field's size, alignment and
  offset; never what the signature help or the header already shows. ~K~
  and ~SPC c H~ show the whole hover with its documentation,
- the offline docs ~SPC s k~ searches, Doom's Dash docsets, install
  themselves in the background the first time a file of their language
  opens, on any machine (=bin/install-docset=, every mirror tried);
  ~M-x +core/install-docsets~ tries again, ~+core-docsets-skip~ leaves
  Boost out; and the daemon at login sets itself up on a machine without
  it (~+core-daemon-at-login~),
- editing defaults: fine-grained undo with the whole history as a graph
  on ~U~, bash tree-sitter mode,
  completion as you type with the first candidate chosen, and what a
  candidate means beside the list on ~M-d~,
- images opened as pictures rather than as their bytes: fitted to the
  window, centred, panned with ~hjkl~, zoomed with ~+~ and ~-~, ~f~ back to
  the window and ~1~ to the picture's own size; SVG through librsvg, so
  the size written into the file is the size drawn, and ~C-c C-c~ edits
  it as the XML it is,
- Doom maintenance in a compilation buffer, with a restart prompt,
- [[https://github.com/kickingvegas/casual][casual]] menus: ~SPC m SPC~ in dired, ibuffer, info, bookmarks, re-builder
  and the agenda shows what that mode can do, ~C-o~ in calc and isearch.

* Menus
Every transient menu closes with =q= or =ESC=, through transient's own
~transient-bind-q-to-quit~ and the ESC binding Doom makes in its magit
module, applied here as soon as transient loads. A menu that had a command
on =q= shows it on =Q= instead; transient does that substitution itself.

A build, a test or a check opens at the bottom and leaves the cursor
where it was; a program's output, =F6= or =SPC k r= in any language, opens
on the right with the cursor in it. =ESC= closes either, from it or from
the source, and so does =q= once nothing is running in it.

* SPC k, the project's keys
=SPC k= opens the keys of the project you are in, from the module that
knows its kind: C and C++, Pascal, Rust or the web, each with the same
letters for the same things, =b= build, =r= run, =R= with arguments, =t=
test, =d= debug, =m= the panel, =n= a new project. A module registers its
map with ~+core-register-builder~.

- In a project no module knows, a Gradle or a Python one, =SPC k= has
  what projection can do with it: build, test, run, install, and the
  menu of its kind on =SPC k SPC=.
- Outside a project, it starts one or goes to one: =SPC k n= a new
  project, =p= open one, =f= a file in any of them, =o= the projects
  folder, =g= clone a repository, =D= forget one.

A project with no version control is known by its files, so a Pascal
folder made without =git init= still has the Pascal keys.

The copy menu also copies the region as a fenced code block with the
path:line on top, the symbol under the cursor, and the forge link.
~SPC f d~ and ~SPC o -~ take Doom's dired keys, on purpose: the file
manager is dirvish either way.

Projectile's file list is not cached: fd lists a project in milliseconds
and a cache goes stale the moment another program adds a file.

Deleting moves to the system's trash (~delete-by-moving-to-trash~): on
Linux the freedesktop one under =~/.local/share/Trash= that Dolphin shows,
on macOS =~/.Trash=, Finder's. So ~D~, ~x~ and ~SPC f D~ can be undone:
~SPC f t~ lists the trash and ~SPC m t~ there moves a file back to the
path it came from. Linux records that path in each file's =.trashinfo=;
macOS keeps it to Finder, so Emacs notes it for each file it deletes
itself, and Finder's Put Back is the way for the rest. macOS lets Emacs
list the trash only with Full Disk Access, in System Settings, Privacy &
Security. ~r~ in dired is ~revert-buffer~, a full refresh, since
=dired-do-redisplay= could leave a dirvish listing looking emptied.

Files go to other apps as files: on Linux as =text/uri-list= through
=wl-copy= (=xclip= on X11), which is what Dolphin, mail and chat clients
read; on macOS as file URLs on the pasteboard, which =osascript= writes,
and Finder reads. The kill ring gets the paths. The same tools bring
files in. The copy menu ~SPC f k~
has both of these too, plus the file's whole text.

The file manager is dirvish, opened with the preview pane by ~SPC o -~
and ~SPC f d~ (~F~ hides it). Images, video frames and audio details are
made with ImageMagick, ffmpeg and ffprobe, which this machine has; with
=vipsthumbnail= installed (package =vips-tools=) images use that, SVG
among them. A picture is shown from a thumbnail within 1000 by 1000,
made once in the background and again when the picture changes; a text
file from its first 64 KB. ~b~
jumps to a quick access entry (home, notes, projects, doom, downloads,
documents, media, scratch, ~+core-quick-access~), and ~SPC m b~ adds the
directory you are in under a letter, kept by savehist in
~+core-quick-access-extra~; the menu is rebuilt through the variable's
own setter, never with setq. ~SPC m 2~ opens a second listing beside the
first, the preview making way; ~C~ and ~R~ then offer the other pane.
The localleader has the symlink and rsync commands dirvish leaves
without a key. ~dirvish-peek-mode~ shows the same preview beside the
minibuffer while choosing a file, the first entry as soon as the prompt
opens: dirvish skipped a file it had previewed last, which the first
entry of ~SPC SPC~ usually was. It waits for the cursor to stop, 0.15 s:
holding a key through the list opens nothing on the way; the file
manager's own pane waits the same. A file can be
dragged out of a listing into another program, a right click is a menu,
wdired edits permission bits, and renaming a tracked file is a git mv.

* Searching and replacing
~SPC s s~ in a file past 2 MB (~+core-search-buffer-max~) asks ripgrep
about the file rather than listing every line of the buffer before the
prompt opens, 1.9 s in a 50 MB log; the view moves to each match all
the same. With changes not saved, or a selection over several lines, it
is the line search.

~SPC s SPC~ is a menu of the searches and of the flags ripgrep takes for
them: a literal string, whole words, case, only the names that match,
only a kind of file it knows, lines of context. consult already passes
on whatever follows a lone =--= in its prompt, which works and has to be
remembered; the menu sets the same flags by name and then searches the
project, this directory, one it asks for, another project, or the word
under the cursor. The flags go to ~+vertico-file-search~ as its ~:args~, which is the way
Doom takes them: it builds ripgrep's whole command line itself every
time it searches, so binding ~consult-ripgrep-args~ round it would be
thrown away without a word.

The same options narrow a replace. ~r~ opens ~+core/replace-menu~, which
asks where with the letters the search column already uses: this
buffer, the project, this directory, one it asks for, another project,
the files marked in dired. A transient only answers for itself, so the
flags are kept in ~+core--kept-flags~ as the replace menu opens and
written at the top of it; ~+core--search-flags~ falls back to them.

Each of those asks ripgrep which files under the place hold the text,
with the flags that are set, and hands that list to ~fileloop~: the
replace visits those files and no others, asking at every match. The
one exception is ~f~, the files marked in dired, which is Emacs's own
~dired-do-find-regexp-and-replace~: it asks for its own regexp, ignores
the flags, and visits every file that is marked. ~F~
makes the text literal by quoting it into the regexp, ~w~ replaces whole
words only, ~i~ ignores case, and the word under the cursor is offered
as the thing to replace. ~SPC s R~ is the project one without the menu.

* The view beside a buffer
A diagram's picture beside its source, an SVG's drawing beside its XML,
an image's structure beside the picture: one piece of machinery, in
=autoload/view.el=. A buffer says how its view is drawn with
~+core-view-enable~ and a function returning an image, text, a command
whose output to show, or work to start in the background and finish with
one of those; core keeps a side window showing the view of whichever
such buffer you are in.

- It opens with the buffer as the command that opened it ends, before
  anything is drawn, so a picture comes up in its place beside it. Shown
  a moment later, it took half the window from a picture already drawn
  across all of it, which spilled out and was fitted again: a jump at the
  first picture of a session. A buffer visited in the background, by a
  search or an export, opens no window.
- A live view is drawn again after a pause in the typing, once per pause
  rather than once per key. A drawing is made in a process of its own
  and shown when it is ready, so the typing never waits for it; one that
  comes back after a newer one was asked for is dropped.
- A picture in it zooms with ~+~ and ~-~, fits with ~f~, takes its own size
  with ~1~ and pans with ~h j k l~, the image viewer's keys. The zoom and
  the place stay while the picture is drawn again, so a detail you zoomed
  into stays in view as you edit. A zoom answers at once, scaled, and the
  sharp picture follows. Pictures are drawn at the screen's own density,
  two pixels to a point on a Retina screen.
- When the drawing fails, halfway through a line, the view keeps what it
  showed and says why in its header, so it never goes blank. When it
  says which line, that line is marked as an error, counted in the
  header with the buffer's other problems and reached with the keys
  that go to the next one; the mark goes once the drawing works again.
- It follows you between buffers that have one, and steps aside for a
  buffer that has none. A buffer says which side its view takes: right
  for a drawing beside its source, left for an image's insides, so the
  picture is on the right either way.
- It is a window you can move into, to scroll a report or zoom a
  drawing; ~q~ in it closes it, and that buffer's view stays closed
  until you open it again, ~+core-view-on-open~ or not. The window is the
  view's alone: a file or a buffer opened from inside it opens in the
  window beside it, a prompt opened there previews in that window, and
  ~SPC SPC~ there lists the project of the file the view shows. Before,
  the next picture took the view's window, and the one beside it was
  split in two.
- The hooks that follow you are on only while some buffer has a view, so
  a session that never opens one pays nothing.

Settings: ~+core-view-side~, ~+core-view-width~, ~+core-view-idle~,
~+core-view-follow~, ~+core-view-on-open~. The diagrams of =:private uml=
use it; so do SVG files and images, below.

* Undo
~u~ undoes one edit, not all that was typed in one go in insert state,
and typing a word at a time, the way VS Code and Qt Creator do: Emacs
gathered up to twenty typed characters into a step and cut it wherever
the twentieth fell, so ~u~ after a sentence left =running f=. A step now
ends where a new word starts; a word longer than twenty letters still
comes back in two.

Emacs keeps every state a buffer has been in, the ones undone too, and ~u~
and ~C-r~ walk one path through them; an edit after an undo puts the rest
out of their reach. ~U~ opens vundo, which Doom installs, on all of them:
a graph along the bottom, newest on the right, the buffer following you
through it. Each branch is a line of the drawing: ~j k~ go to the line
below and above from any state, onto the state drawn nearest, ~H L~ to
the ends of the line; ~h l~ older and newer, ~l~ at a fork back down the
branch ~h~ came up. ~s S~ the states that were saved, ~d~ a diff of what
the state changed that follows as you move until ~d~ again, ~m~ a state
to diff against instead. ~RET~ keeps where you are, ~q~ and ~ESC~ put the
buffer back; the keys are in the graph's header. ~SPC t u~ shows the
graph for a moment at each ~u~ and ~C-r~, for every buffer.

After ~u~, ~C-r~ and each step through the graph the lines that changed
light up for ~+core-undo-flash-time~ (0.3 s): an undo only puts the
cursor at one end of what it changed.

The graph is drawn anew each time and its first drawing is most of its
cost: 200 ms for 3 400 states, about the most a buffer holds under Doom's
~undo-limit~ of 256 KB, since the check for compositions, the cursor flash
and garbage collection were taken out of it (600 ms before); a step
through it is a millisecond, a diff 20 ms. A longer history would draw
longer, so the limits stay Doom's; vundo says so when a collection has
trimmed the oldest states.

A step the history can no longer make, when what it recorded does not
match the text any more, used to fail at every key: each move tried it,
and ~q~ as well, since going back to where you started takes it again,
so only ~RET~ got out. Such a step now says so and the graph is drawn
again from the text as it is; ~q~ that cannot go back keeps the text and
closes the graph, and ~RET~ always leaves. The diff at the oldest state
says there is nothing before it, rather than keeping the last one up.

* Pictures
An SVG opens as its XML with its drawing on the right, over a mid-grey
checkerboard so a transparent icon shows on any theme, a white one
included. Any other image opens as the picture on the right with
=bin/inspect-image='s report on the left: the picture's size, shape and
compression, its colours, its structure chunk by chunk or marker by
marker, exiftool's metadata, and its bytes in hex. The cheat sheet's
Images section has the keys.

The drawing is made by =rsvg-convert=, librsvg's own program, in a process
of its own: in the editor a 1.8 MB drawing took 2 to 3 s at each pause,
drawn four times over, and now the typing never waits. Its size comes
from the XML, never from drawing it. Without =rsvg-convert= Emacs draws it
itself, once per pause, and says so once. The element the cursor is in
is outlined in the drawing, in the cursor's colour, a line of the same
width at any zoom; ~SPC m P h~ turns it off.

* Data files
~SPC m v~ says whether a JSON, YAML, TOML, XML, CSV or INI file is valid
and takes you to where it is not; ~SPC m =~ and ~SPC m -~ reshape it,
keeping its comments. Validation is =bin/check-data=, one program that
reads each format with its own parser, kept outside Emacs so it can be
run over every data file on the machine. The language servers check as
you type, against SchemaStore; the JSON one is handed the catalog here,
since unlike the YAML one it does not fetch it. The cheat sheet's Data
files section has the detail.

* Configuration
- ~+core-transparency-alpha~, 85 by default.
- ~corfu-auto~ is on, 0.15 s after two characters, ~corfu-preselect~ is
  ~first~ so ~RET~ takes the candidate; ~SPC t a~ makes it manual, ~C-SPC~.
- ~+core-notes-dir~ (=~/org/=, set for this machine in =init.el=) and
  ~+core-projects-dir~ (=~/projects/=): where the notes and the projects
  live; the notes module and the C++ scaffolds read them.
- ~+core-undo-flash-time~ (0.3 s), how long the lines an undo changed stay
  lit; 0 lights none. ~vundo-window-max-height~ is 10 lines.
- ~+core-treesit-unparsed-max~ (256 KB): past this size a file
  tree-sitter cannot parse, or takes longer than
  ~+core-treesit-reparse-max~ (0.04 s) to reparse after an edit, opens in
  the older mode; so does one with a
  node of more than ~+core-treesit-children-max~ (20 000) children, an
  image as a C array, whatever its size. ~+core-large-file-size~ (1 MB)
  says what is large.
- ~+core-long-lines-mean~ (100): a code file whose lines average more
  characters than this keeps its mode, colour and language server but
  wraps its lines, composes no glyphs, and has no header line (the ui
  module, from ~+core-long-lines-hook~). A table of 2 000 character
  rows: 100 to 230 ms a key to 4 to 14, a line moved 83 to 108 ms to 15
  to 27, a =j= now passing a whole wrapped line (=gj= a screen line, 1
  ms). Doom's so-long, past 10 000 characters, still opens plain text.
- ~+core-build-niceness~ (10): builds start under =nice= at this value,
  so typing goes first when the cores are short. Every compilation is a
  build but a run (a =*run...*= buffer, projection's run), a benchmark
  and one that takes input; a search is not a compilation here. A re-run
  with =g= keeps what the first run was. The command reads as written.
  nil starts builds at the editor's own priority.

* The shared library
=autoload/lib.el= holds what the other private modules ask core for, one
answer each: ~+core-project-root~ (the VCS root, else the topmost CMake or
PlatformIO directory, remembered for ~+core-project-root-memo-seconds~
since projectile walks the whole tree for a directory without a
repository; ~+core-project-root-or-nil~ is the same with no fallback),
~+core-file-at-point~ (dired marks, the file at point, this file),
~+core-compile~ (a compilation buffer that carries its name in
~+core-compile-name~), ~+core-last-compilation-buffer~ (the build, test
or run that started last, whoever started it), ~+core-run-in-vterm~,
~+core-git~ and ~+core-git-state~ (no-repo, stopped, dirty, clean),
~+core-todo-regexp~, ~+core-language~ (a mode's language for a fenced
block or a babel block, one table, ~+core-languages~).
core loads first in the =:private= block and every one of them is
autoloaded, so a module calls them without a declaration.

* Working on the config
Three habits keep the config sound, each backed by a check:

- A config file must survive =SPC h r r= (~doom/reload~): a form that
  appends to a list, adds a hook or starts a timer runs again on reload,
  so it removes its own entries first, or keeps a handle it cancels.
  Twice a reload doubled a list here (dc7a3ca, the capture templates);
  =bin/check-config= reloads twice and names what this config grew.
- A function bound, hooked, advised or listed in =config.el= but defined
  in =autoload/= needs its =;;;###autoload= cookie, or the first use is
  void in a fresh Emacs; =doom sync= does not notice. =doom doctor=
  reads the modules for that, and =SPC h d C= asks the running session.
- A commit is one change, =type(scope): what=, no trailer. The what is
  written in the imperative, as an instruction to the code: =add=, =drop=,
  =keep=, =stop=, =say=, =make=. The scope is never left off: it is the
  module the change belongs to, or =project= when the change is across
  the tree.
  =bin/check-commit-msg= refuses the rest once linked as
  =.git/hooks/commit-msg=.
- Every =package!= carries a =:pin=, the commit installed here, so =doom
  sync= on another machine installs the same versions and an upgrade is a
  decision: =M-x doom/bump-package-at-point= on the line (or
  =doom/bump-packages-in-buffer=) moves the pin to the newest commit, then
  =SPC h r s= installs it. =SPC h r u= updates Doom and its own pins and
  leaves the private packages where they are.

=doom doctor= also names the tools and fonts each module wants, and
=bin/check-config= (run on the host after =doom sync=) starts a throwaway
daemon, byte-compiles every private file into a temporary directory,
reports the compiler's and the startup's complaints, lists the repeating
timers, asks whether every referenced function is callable, and reloads
the config twice to name any list, hook or timer of this config's that
the second reload grew: ten seconds, the check to run after any large
change.

* Performance
Measured on 2026-09-17 in a fresh frame: a 47 MB log opens in 216 ms
(fundamental mode, as Doom arranges for big files), 200 cursor moves in it
30 ms; a 2 MB C++ file opens in 1.3 s (the tree-sitter parse), 20 page
downs 52 ms; a 155 KB org file opens in 188 ms; the fdc project's 1684
files list in 92 ms; a C++ buffer of that project comes back in 338 ms and
its server, started in the container, attaches within half a second; a
cursor move in dired costs 2 to 6 ms.

Measured again on 2026-09-27, in a 1 547 line C++ file of the fdc
project with clangd attached, key and redisplay together: a line move
9 ms, a half page 13 ms, a keystroke 14 ms, where they were 28, 35 and
37 before the two changes at the end of the list below. A header that
tree-sitter's C++ grammar cannot parse, nlohmann's 24 765 line

at every keystroke, 43 ms; it opens in cc-mode now, below.

The same day, across the modes with their servers attached, a keystroke

337 to 87; Enter in C++ 27 to 9.5.

What keeps it that way:
- No repeating timer runs for a buffer nobody sees: every timer wake is a
  redisplay, which in a busy window costs tens of ms. The dashboard
  animation stops off screen; the butler wakes once per step.
- A dirvish listing draws its icons and sizes again only where something
  changed, the line the cursor left and the one it is on when only the
  cursor moved. It made them all again before every redraw, and any
  overlay change lays the window out afresh, so a listing on screen kept
  a third of a core busy doing nothing. At load 25: idle 16 ms in every
  40 to 1, =C-d= 31 to 64 ms to 13 to 28, a held =j= 24 to 31 to 10 to
  18, a step with its preview 93 to 116 to 48.
- ~eglot-sync-connect~ is nil: the buffer comes back at once, the server
  attaches when ready, instead of a one second wait on every first open.
  A second file of the project opened while its server is still on its
  way, a header straight after its source, waits for that server
  instead of starting another; one of the two used to die, and say so.
- What the first file of a session loads is loaded while Emacs waits
  after starting, a step at a time, each giving way to a key: eglot and
  its libraries, version control and the diff gutter, which-key and the
  completion, then the mode of the latest recent file in a tree-sitter
  mode, set up once in a hidden buffer so its queries are compiled and
  its snippets read, and the files the modules load for it
  (~+core-warm-up-features~, ~+core-warm-up-functions~).
- The answers that cost a trip into the container, what each kit's qmake
  says and where a container keeps its home, are kept across sessions:
  a second of the first C++ file of every session. =SPC k m Z=
  (~+cpp/forget-kits~) asks again.
- eldoc primes its list of motion commands with one regexp over all the
  symbols, in C, not thirty passes over them: 30 ms, not 235 to 581.
- Doom compiles a few of its hot functions when Emacs is idle; they are
  byte-compiled in place now, not natively in a batch Emacs waited for,
  a third of a second frozen each.
- clangd indexes at low priority, on every core.
- dired marks each file's git state in the fringe. It runs git twice per
  file in the background as a directory of a repository is entered, 12 ms
  a file on the Mac, off the editor's thread; the old machine at load 30
  could not spare the core.
- Tree-sitter grammars for the enabled modes are installed ahead of time,
  so no first open compiles one; ~treesit-auto-install-grammar~ stays
  ~always~ for the next language. (Not listed here: the list rots.) A
  file only previewed never builds one, whoever would ask: on a new
  machine every language's first preview froze while its grammar was
  cloned and compiled, 1.5 s for Go and CSS, more for TypeScript.
  A buffer past tree-sitter's limit, ~treesit-max-buffer-size~ (40 MB),
  gets the older mode with nothing installed: Doom took the limit for a
  missing grammar, and built the C++ one again at every such file.
- Projectile has no cache; fd lists a project in milliseconds.
- gcmh lets 64 MB of garbage gather at rest and 256 MB at work, 512 with
  a language server, which Doom doubles it for: a collection of a 178 MB
  heap took 176 ms at 16 MB and 181 at 64, and comes half as often; at
  256 MB a quarter as often again, 219 ms. With memory to spare, fewer
  pauses of the same length are the better trade.
- gcmh collects after four seconds of rest. Doom's setting waits ten
  times the last collection, under half a second here, so every pause to
  read a line ended in a collection of 40 to 150 ms that the next key
  waited for.
- The blame at the end of the line is one =git blame= of the whole file,
  kept, not a second Emacs started for every line the cursor rests on;
  that was a third of the editor's time while moving through a file.
- eglot stays out of imenu: the header line's breadcrumbs asked the
  server for every symbol of the file after each edit, a five second
  freeze at every pause in a large JSON file; tree-sitter's index is
  local. It finds the positions a server sends by counting from the last
  one found rather than from line 1, which made a long list cost the
  square of the file's length. Its "a fix is available" mark asks about
  the symbol at point, where it walked every sibling in the syntax tree
  to find the expression around it. And no server formats as you type:
  that was a round trip waited for at every newline.
- Inlay hints, the parameter names before the arguments, are asked for
  the whole file when they come on, in blocks of 300 lines from the one
  on screen, and for the screen again after an edit; eglot asked a
  screen at a time as each part was first drawn, so scrolling sent a
  request at every page and the text moved as the names came in. Text
  changed off screen, by a format on save, a rename or a revert, has
  its blocks asked for again once the keys rest. ~SPC k l i~ twice asks
  for the whole file again.
- The header line finds the function around the window's top in the
  syntax tree, as many steps as the tree is deep, not by moving to the
  start and end of a defun past every sibling.
- The snippet completion looks eighty characters around point for a key,
  not from the top of the buffer at each attempt.
- Past 300 diagnostics in a report none is written at the end of its
  line; rewriting 1 607 of them at each report doubled a key's cost.
- The minimap is a copy of the buffer, not demap's indirect buffer, which
  every overlay the file moved redrew: 8 ms a key with it open, 0 now.
- Completion runs after a pause of 0.15 s, not on every keystroke.
- Backspace in the popup deletes a character. Doom makes it reset the
  popup whenever a candidate is chosen, for the preview it inserts;
  with the first chosen from the start that was every backspace.
- ~large-file-warning-threshold~ is 64 MB; below that, files just open.
- A file of more than 20 000 lines gets so-long's minor mode, Doom's
  rule: eldoc, smartparens, whitespace trimming, the jump list and
  save-place go, and it colours less. In 28 000 lines of C++ a key costs
  13.5 ms so, 19 to 28 without (2026-10-23). =M-x so-long-minor-mode=
  gives it all back in one. A file over a megabyte is marked large in its
  own buffer, ~+core-large-file-p~; Doom's mark never fired on Emacs 31.
  The mark only keeps the header line from looking for the function
  without a syntax tree.
- A file tree-sitter would make slow opens in the mode Emacs had before
  it: one over 256 KB (~+core-treesit-unparsed-max~) that it cannot
  parse, or that it takes more than 40 ms to reparse after a one
  character edit, timed as the file opens (~+core-treesit-reparse-max~);
  and one with a node of more than 20 000 children. Tree-sitter reparses
  what an edit touched, and in a file that is one declaration, or one
  error, or thousands of errors, that is all of it: a generated 1.5 MB C
  file reparsed in 90 ms and took 190 a key, 8 in c-mode.
- A file past two megabytes (~+core-plain-file-size~) is made by a
  program, and opens whole as plain text, at once: its mode went over
  all of it before the first screen, 2.4 s for 8 MB of C++, 2.3 s for
  2.5 MB of Org, and cc-mode spent minutes on one key in a 50 MB Qt
  resource. =M-x +core/file-own-mode= gives it its mode, which a revert
  keeps; an SVG keeps its drawing. Pictures, PDFs, archives and Org
  files, which the agenda reads in org-mode only, are not touched. Reading such a file in pieces behind the first screen was
  measured and is worse: each piece sends the mode over the whole file
  again, 8.8 s in all for that C++ and 40 s for an 8 MB JSON.
- A file previewed, beside ~SPC .~, in the file manager's pane or in a
  search, is plain text, whatever it is and whatever its size: its mode
  is never set up, so nothing it runs can hold the cursor up. A font
  kept as a C array took 115 to 390 ms to show in ~c-ts-mode~, a 900 KB
  header a third of a second to colour at each step; plain, a preview
  takes a millisecond. Pictures, videos, PDFs and fonts are drawn by
  their own programs outside Emacs, a GIF as its first frame; a binary
  says so in a line, a pipe or a socket is not read. A search reads a
  file whole up to 8 MB: past a megabyte consult showed its first 10 KB,
  so a match further down was not on screen. The file picked opens
  afresh, in its own mode.

Doom's own part, left as it is: ~read-process-output-max~ 1 MB under eglot, native
compilation of every package ahead of time, so-long and fundamental mode
for huge files, ~redisplay-skip-fontification-on-input~.

When something pauses now and then: ~SPC t W~ watches, writing down every
key, timer and garbage collection that takes over
~+core-latency-threshold~ (50 ms), with the buffer and mode; ~SPC h D~
shows what it caught.

When something is slow: =M-x profiler-start=, do the slow thing, =M-x
profiler-report=. In a running session, =emacsclient -s server -e= can run
the same from outside, and =/proc/PID/stat= over a few seconds tells
whether Emacs is busy while idle.
